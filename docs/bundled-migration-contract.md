# Контракт поставляемых миграций

В `Module.migration_policy` поддерживаются `none`, `client` и `bundled`.
Режим `bundled` сохраняет исходные миграции при генерации и не включает
приложение в список первичной генерации миграций. Отсутствие исходной
истории приводит к отказу генератора. Пока существующие приложения
PrimaryKit остаются на `client`; перенос в `bundled` требует
проверки PostgreSQL, согласования ссылок на `users` и отдельной процедуры
для уже созданных клиентских проектов. Особенно важно не смешивать
standalone/tenant графы `catalog` и `inventory`.

## Проверка применённых миграций PostgreSQL (только чтение)

В новых проектах **Tasks** уже использует `bundled` с фиксированной миграцией `0001_initial.py`; другие модули требуют самостоятельной проверки контракта, а старые клиентские миграции нельзя перезаписывать.

Для контроля существующего проекта доступна **необязательная** сверка файлов миграций с реальными записями `django_migrations`:

```bash
# Из доверенного клона PrimaryKit:
export DATABASE_URL='postgresql://audit_user:...@db.example/client_db'
python scripts/migration_adoption.py --source . --project ../customer-backend \
  --verify-postgres --strict
```

При отсутствии `--verify-postgres` проверка остаётся полностью офлайн. При включении флага открывается соединение к явно выбранной БД с `default_transaction_read_only=on`, таймаутом запросов 5 секунд и проверкой режима чтения. Выполняется **только SELECT** из `django_migrations`; миграции и любые изменения схемы не запускаются. Рекомендуется отдельный пользователь БД только с правом `SELECT` на эту таблицу, безопасное соединение и проверка адреса базы перед запуском. Пароль и строку подключения не публиковать.

Отчёт определяет неполные, отсутствующие, неожиданные и оставшиеся после удаления модуля записи миграций. `--strict` возвращает ошибку, если необходим ручной аудит. PostgreSQL CI теперь проверяет этот отчёт во всех девяти конфигурациях генерируемых проектов.

**Важно:** совпадение таблицы `django_migrations` и файлов не доказывает, что настоящая схема, индексы, зависимости, данные или история старого клиента совместимы с новой версией. Перед переносом миграций необходимы отдельное ревью, резервное копирование и проверка на копии БД. Issue #88 пока остаётся открытым.

# Version-aware source updates and reviewed three-way apply

New generated projects record source Git SHA, per-module source refs and
fingerprints in `primarykit-origin.json`. These are audit metadata, not runtime
dependencies. Generate from a trusted Git checkout and retain its full history.

```bash
python scripts/module_upgrade.py --source . --project ../client --three-way-plan --json
# Work on the CLIENT repository; start with committed changes and a feature branch.
git -C ../client switch -c chore/primarykit-module-upgrade
python scripts/module_upgrade.py --source . --project ../client --apply-three-way --json
git -C ../client diff --check
git -C ../client diff
# Commit the client changes, run pytest/PostgreSQL CI, and open a client PR.
```

The opt-in apply refuses dirty client or source trees, the default branch, missing
or unrelated immutable Git ancestry, historical blob hashes that differ from
recorded provenance (including source-only changes), ambiguous conflict merges,
changed schema contracts, source deletions, unreviewed module migration histories
(unless explicitly accepted, see below),
unsafe symlink paths and invalid Python. Keep the original source Git commits
locally available, including history older than the current checkout. Clients'
independent local changes are preserved.
Client hashes and module ancestry advance to the incoming source version only
after all staged replacements succeed; otherwise changes are rolled back.

This tool **does not create Git commits, push code, open a PR, resolve schema
migrations, or deploy**. It writes only non-contract Python to a reviewable
feature branch. The client owner must review the resulting diff, test with
PostgreSQL, commit and create its own pull request.

## Reviewed acceptance

Contract and schema changes stay refused unless a human has already placed
them in the client branch and names the module:

```bash
python scripts/module_upgrade.py --source . --project ../client --apply-three-way \
  --accept-reviewed MODULE... [--merged-path MODULE/PATH]... \
  [--keep-client-migrations MODULE...]
```

Contract files are still never written. For an accepted module the tool checks
that every upstream contract change is either byte-identical in the client or
listed as a hand merge in `--merged-path`, verifies the same immutable ancestry
as for merges, and only then advances fingerprints, the module source ref, the
module version (from the source commit's `pyproject.toml`) and
`module_migration_policies`. An unplaced contract change, an unconfirmed
two-sided change, an unused `--merged-path`, an upstream deletion still
present in the client, an unknown baseline, symlinked provenance or an
unreadable version aborts the batch before any write. Acceptance records a
human claim; it does not verify that the review was adequate. Steps, the
migration-history decision and limits:
[updating copied modules](module-updates.md#accepting-reviewed-contract-changes).

## Evidence and what is still open

`scripts/ci_release_upgrade.py` upgrades PostgreSQL clients generated by three
historical commits (`scripts/release_baselines.json`) to the current catalog
with seeded rows and client customizations. That covers the earlier
"three-version stateful PostgreSQL upgrade" item for six modules, with a
scripted reviewer and commit-pinned baselines.

Still required before #89 and #88 can close: published tagged SemVer releases
as baselines, human-run upgrades of real clients, a schema-changing upgrade
with a data migration, more bundled modules, tenant-mode graphs and rollback
verification. Tenant/standalone conversion remains unsupported. The feature is
a fail-closed lifecycle milestone, not a production migration mechanism.

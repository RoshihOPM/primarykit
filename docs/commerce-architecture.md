# Commerce в PrimaryKit: Orders, Sales, Payments

Три **самостоятельных переносимых Django-модуля**. Каждый работает на основе Users/Core и не имеет обязательных FK на соседние контексты. Сочетать их можно, но установка одного **не активирует** автоматически другой.

> **Версия v1 — backend учёта/проектная основа, а не готовый интернет-магазин и не платёжный шлюз.** Публичный checkout, доверенные цены из прайс-листа, эквайринг, возмещение денег, фискализация и списание товара требуют дальнейшей интеграции.

## 1. Модель

| Модуль | Основные модели | Назначение |
| --- | --- | --- |
| `orders` | `Order`, `OrderItem` | Снимок состава заказа и цен |
| `sales` | `Sale`, `SaleLineItem` | Независимый учёт факта записи о продаже |
| `payments` | `PaymentIntent`, `PaymentEvent` | Создание намерения и привилегированная сверка результата |

Все денежные значения `*_minor` — **целые числа минимальной денежной единицы указанной валюты**, например 100 для USD 1.00. В этой версии `currency` — трёхбуквенный код в верхнем регистре; приложение проверяет формат, но не глобальный список ISO 4217 и не количество дробных разрядов каждой валюты. Для KZT обычно передают сумму в тиынах. Библиотека **не выполняет конвертацию валют**.

Клиент создаёт Order/Sale с `sku`, `title`, `quantity`, `unit_price_minor`. Сервер валидирует и сохраняет неизменяемый снимок строк на момент создания (строки API редактировать нельзя). Эти значения **поступают из запроса**, поэтому **не считайте их проверенной ценой каталога** — для настоящего checkout подключите серверную проверку цены/скидок и пересчёт налога.

Каждый контекст хранит `owner=User` и свои идентификаторы. `Sale.source_order_id` и `PaymentIntent.source_order_id` — **необязательные UUID**, не внешние ключи к чужим моделям. Если Orders подключён, сервис обязательно проверяет owner, статус заказа, валюту и итоговую сумму перед записью связи. Чужие заказы недоступны и для прямых сервисных вызовов.

## 2. Жизненный цикл

```text
Orders                        Sales                      Payments
placed ───────► canceled      recorded ─► voided         pending
                                                           ├──► canceled
                                                           ├──► succeeded
                                                           └──► failed
```

- `orders.cancel` запрещается, если уже есть успешная оплата, требующая refund. В v1 нет полноценного refund flow; оплаченное не отменяем одним API-запросом.
- `sales.void` помечает запись учёта аннулированной. Это **не возврат денег, не фискальный возврат и не восстановление остатков**.
- `payments.succeeded` возможен **только после привилегированной подтверждённой сверки**, а не из обычного POST клиента; публичный webhook пока отсутствует.
- `orders` **не резервирует склад**, а `sales` **не списывает Inventory** автоматически. Для этого нужен отдельный use-case с компенсацией и идемпотентностью.

## 3. Настройка

В исходном конструкторе:

```bash
uv run python scripts/new_project.py ../shop-api --name shop-api \
  --apps orders sales payments statistics audit --git-init
cd ../shop-api
cp .env.example .env
docker compose up -d db
uv sync --locked
uv run python manage.py makemigrations users orders sales payments audit
uv run python manage.py migrate
uv run python manage.py runserver
```

Можно добавлять по одному: `python manage.py install_kit_module orders --source ../primarykit`, затем `makemigrations orders`, `migrate` и restart. Модули автоматически подключаются через `manifest.py`; тестовый пример исходит из backend-проекта **на базе PrimaryKit**.

## 4. API Orders

```http
POST /api/v1/orders/
Authorization: Bearer <JWT>
Content-Type: application/json

{
  "currency": "USD",
  "idempotency_key": "checkout-00000001",
  "lines": [
    {"sku": "TEA-01", "title": "Tea", "quantity": 2, "unit_price_minor": 125}
  ]
}
```

Ответ включает `status=placed`, `total_minor=250`, UUID, даты и строки.

- `GET /api/v1/orders/` — список собственных заказов.
- `GET /api/v1/orders/{id}/` — детальная информация только владельцу.
- `POST /api/v1/orders/{id}/cancel/` — отменить `placed`, если нет успешного связанного платежа.

`idempotency_key` уникален в рамках пользователя: точный повтор возвращает прежний ресурс, повтор с другим составом даёт 400. Ключ стоит генерировать на одно бизнес-намерение, а не на каждую HTTP-попытку.

## 5. API Sales

```http
POST /api/v1/sales/
Authorization: Bearer <JWT>
Content-Type: application/json

{
  "currency": "USD",
  "idempotency_key": "sale-00000001",
  "source_order_id": "<optional UUID of own placed order>",
  "lines": [
    {"sku": "TEA-01", "title": "Tea", "quantity": 2, "unit_price_minor": 125}
  ]
}
```

`source_order_id` необязателен. Если он передан, Orders должен быть установлен, и сервис проверяет, что заказ собственный, не отменён, совпадают валюта, сумма и все строки (SKU, название, количество и цена). Для одного заказа допускается одна запись Sale.

- `GET /api/v1/sales/` и `/{id}/` — только собственные продажи.
- `POST /api/v1/sales/{id}/void/` — пометить запись аннулированной. Не отменяет payment и stock.

## 6. API Payments

```http
POST /api/v1/payments/
Authorization: Bearer <JWT>
Content-Type: application/json

{
  "currency": "USD",
  "amount_minor": 250,
  "idempotency_key": "pay-00000001",
  "source_order_id": "<optional own placed order UUID>"
}
```

Ответ всегда `status=pending` до доверенной сверки.

- `GET /api/v1/payments/` и `/{id}/` — только собственные платежные намерения.
- `POST /api/v1/payments/{id}/cancel/` — отменить только `pending`.
- `POST /api/v1/admin/payments/{id}/reconcile/` — **только Django superuser**, ручное подтверждение доверенного внешнего факта: `event_key`, `outcome` (`succeeded` или `failed`), `amount_minor`, `currency`.

Запись `PaymentEvent` неизменяема через модель. Повтор подтверждённого `event_key` идемпотентен; конфликт ключа или неверная сумма отвергаются. Этот маршрут — **ручная административная операция для разработки/закрытых сценариев**, не публичный callback платёжного провайдера. Ключи и сведения о статусе в клиентском запросе не являются подтверждением денег.

### Что обязательно для production-платежей

1. Выбрать реального провайдера (например, банковский эквайринг) и реализовать отдельный backend adapter.
2. Проверять криптографическую подпись и идентификатор merchant/provider, оригинальное тело запроса, replay-window и источник события.
3. Сверять provider transaction ID, merchant account, сумму/валюту и внутреннее намерение с серверными ценами.
4. Сохранять idempotent webhook-инбокс, обработку повторов и reconciliation для асинхронных/потерянных уведомлений.
5. Реализовать refunds, chargebacks, частичные платежи, отмену заказа/склада, merchant ledger и финансовые отчёты.
6. Исключить ручную сверку из публичных production-процессов; держать её за MFA, аудитом и отдельными RBAC/операторскими процедурами.

**Пока этого нет, Payments нельзя считать реальным платежным решением.**

## 7. Безопасность и ограничения

Все API требуют JWT. Владелец видит только свои записи; суперпользователь **не получает личные данные чужих клиентов** через пользовательский API. Административный `reconcile` — исключительная явно привилегированная операция. Переходы статусов проверяются в транзакционных сервисах с блокировкой владельца и нужной записи, чтобы повторные/параллельные запросы не создавали дубли.

Глобальная мультиарендность Orders/Sales/Payments пока **не реализована**: наличие Organizations в проекте само по себе не создаёт корпоративный доступ, права кассира/продавца или привязку заказа к филиалу. Для этого потребуется отдельная безопасная tenant-архитектура.

## 8. Statistics

Если установлен Statistics, модули автоматически дают личные метрики:

- Orders: количество, активные `placed`, новые за период.
- Sales: количество записанных `recorded`, новые записи за период.
- Payments: число `pending` и подтвержденные `succeeded` за период.

**Внимание:** мы намеренно не добавили агрегат общей выручки: суммирование разных валют в одну цифру финансово некорректно. Для мультивалютного продукта нужна группировка по `currency`, отдельные финансовые права и отчёты.

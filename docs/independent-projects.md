# Независимость сгенерированных проектов

## Обязательное правило

PrimaryKit — **одноразовый источник копируемых файлов**, а не runtime SDK, центральный backend, SaaS или обязательный сервис обновлений. После генерации исходный репозиторий, GitHub-доступ к нему и его CLI **не нужны** для запуска, тестирования, сборки и деплоя нового backend.

- Собственные `apps/`, `config/`, `pyproject.toml`, `uv.lock`, Docker, CI, окружения и git-история.
- **Нет** импортов вида `from primarykit...`, `import primarykit` в runtime, package/runtime dependency `primarykit`, скрытых URL/API вызовов в конструктор.
- `primarykit-origin.json` — только необязательное происхождение исходников, его можно удалить. Это не версия клиентского продукта и не контракт обновления.
- Каждый проект создаёт, ревьюит и коммитит **собственную историю миграций**. База клиента никогда не управляется каталогом.
- Любое обновление скопированного исходника выполняется вручную в **клиентском репозитории**: сравнить diff, учесть кастомизации, миграции, тесты, собственный PR и release.
- Можно полностью переделывать модули, удалять ненужные и добавлять бизнесовые приложения. Общей схемы Order/Payment/Inventory для всех компаний **не существует**.

## Граница типового функционала и бизнес-логики

Users/Auth, Storage, Notifications, Audit, RBAC и Core — технические стартовые реализации. Orders/Sales/Payments, Catalog/Inventory — **примеры предметных контекстов**, не нормативная бизнес-модель. Не создавайте обязательный FK между независимыми контекстами только потому, что они были выбраны вместе.

Примеры: в автомаркете заказ может означать запрос на просмотр, в сервисе доставки — заказ перевозки, в магазине — покупку с резервом склада. Каждая реализация живёт и изменяется **в проекте конкретного бизнеса**, а не в PrimaryKit. Включение Organizations не даёт автоматически tenant-scoping для Orders/Sales/Payments; он должен быть явно реализован и протестирован.

## Проверка без конструктора

```bash
cd ../my-api
python -m apps.core.doctor --strict
python -m apps.core.doctor --json
uv sync --locked --all-groups
uv run python manage.py check --settings=config.settings.test
uv run pytest
```

`doctor` работает без старта Django/БД/сети и без самого PrimaryKit: проверяет manifests, baseline, hard dependencies, циклы, tenant schema modes, отсутствие runtime импортов/dependencies конструктора и, если есть, информационный metadata-файл. `--strict` также блокирует предупреждения. Это **не** проверка применённых миграций, боевой безопасности, доступности БД/S3 или корректности бизнес-логики.

Обязательно проверяйте в отдельной директории после удаления или отключения исходного checkout. Тесты генератора и CI дают автоматическую выборочную проверку независимости.

## Жизненный цикл

1. Выбрать базовые модули; сгенерировать новый проект.
2. Запустить offline doctor, locked sync, Django checks и unit tests.
3. Разработать собственные модели, политики доступа, доменные правила и интеграции.
4. Создать initial migrations **только в клиентском проекте**, проверить и сохранить в Git.
5. Развернуть проект со своей БД и инфраструктурой; конфигурировать TLS, секреты, бэкапы.
6. Исправления конструктора не распространяются автоматически; при необходимости **ручной перенос изменений** через PR с собственным CI.

**Запрещено:** installer/updater, который незаметно перезаписывает клиентскую бизнес-логику, включает модули, меняет режим схемы или запускает production миграции.

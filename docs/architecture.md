# Архитектура PrimaryKit

**Язык:** Русский · [English](en/architecture.md) · [Оглавление](README.md)


## Границы

- `config/`: Django project settings, ASGI/WSGI, URL routing. Это **Django Core**.
- `apps/core/`: переносимые абстрактные модели, API utilities, healthchecks.
- `apps/users/`: account bounded context с email-идентичностью, JWT, восстановлением и проверкой email.
- Другие `apps/`: автономные бизнес-возможности, без ссылок на клиентские сущности.
- `docker/`, `compose*.yaml`: инфраструктура, dev/prod отдельно.

## Контракт нового модуля

Модуль включает `domain.py` для **существующих нетривиальных инвариантов** без импортов Django/DRF/ORM, `services.py` как application layer для команд и транзакций и Django/DRF адаптеры (`models.py`, `views.py`, `serializers.py`). Допускаются `ports.py` и `gateways.py`, если есть внешняя зависимость, например email. Простому CRUD не требуются пустые классы и папки. См. ADR 0003.

Внутри модуля допустимы зависимости на Core и явно объявленные модули. Запрещены импорты моделей конкретного клиентского проекта. Все ограничения доступа проверяются на сервере.

## Политика миграций

PrimaryKit предназначен для **копирования исходного кода** в новые репозитории, а не для обновления общих установленных пакетов. Библиотека хранит схему моделей без исторических миграций. В каждом новом проекте:

1. Выбрать Apps и настройки **до** первого запуска миграций.
2. Сгенерировать миграции для `users` и остальных установленных модулей.
3. Выполнить `migrate`.
4. **Закоммитить все созданные миграции** в новый проект.
5. При последующем обновлении модуля проводить schema review и новые миграции проекта.

`AUTH_USER_MODEL = "users.User"` установлен сразу: менять user model после старта миграций крайне рискованно.

Отсутствие миграций в исходном репозитории — осознанный trade-off: сложные data migrations, upgrades и начальные данные оформляются отдельно.

## Окружения

- `local`: local development only.
- `test`: SQLite in-memory для быстрых unit/smoke tests; PostgreSQL integration tests уже используются в CI для конкурентных операций, но нужны и в тестах каждого клиентского проекта.
- `production`: требует секрет, разрешённые хосты, БД, TLS через reverse proxy, сессии/CSRF только по HTTPS.

`DATABASE_URL` в Compose должен соответствовать параметрам PostgreSQL; для пароля со спецсимволами потребуется URL-кодирование или другой способ задания настроек.

## Дальнейшие шаги

- `uv.lock` хранится в репозитории. При изменении `pyproject.toml` выполняйте `uv lock` и коммитьте lockfile. Docker/CI используют `uv sync --locked`.
- CI уже содержит проверки Compose + PostgreSQL; клиенту дополнительно нужно выполнять production `check --deploy` со своими настройками.
- Users, RBAC, Notifications, Audit, Storage, Organizations, Catalog and Inventory уже реализованы. Catalog и Inventory имеют два режима: standalone (владелец) и tenant (компания/филиалы). Storage поддерживает раздельные персональные и корпоративные файлы через политику доступа.
- Генератор модулей поддерживает полностью независимые Catalog и Inventory. Для корпоративного комплекта нужно явно выбрать `catalog inventory organizations` и до первой миграции закрепить tenant-режим.

## DDD и проверяемые границы

В `apps/*/domain.py` находятся чистые Python-правила. HTTP и Django ORM не импортируются в этот слой. Сервисы реализуют применение правил, транзакции, авторизацию, аудит и работу с моделями. Входящие и исходящие адаптеры могут использовать Django/DRF; для внешних инфраструктур определяются порты (`notifications.ports.EmailGateway`). Все изменения сохраняют действующие API и таблицы; критические инварианты дополнительно проверяются внутри сервисов, а не только сериализаторами. Автоматический тест `apps/core/tests/test_ddd_boundaries.py` проверяет чистоту импортов и бизнес-правила как в полном каталоге, так и в сгенерированных вариантах.

См. [ADR 0003](adr/0003-implemented-ddd-boundaries.md).

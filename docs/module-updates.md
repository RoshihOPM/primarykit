# Безопасное обновление скопированных модулей

Код, история миграций и эксплуатация остаются под контролем клиентского
проекта. Используйте **доверенную копию PrimaryKit с доступной историей Git**.
Команды обновления запускаются из исходного репозитория, но работают с
отдельным клиентским проектом.

## Проверка без изменений

```bash
python scripts/module_upgrade.py --source . --project ../client-api --json
python scripts/module_upgrade.py --source . --project ../client-api --three-way-plan --json
```

Отчёт классифицирует изменения источника и клиента. План трёхстороннего
слияния дополнительно проверяет исходные Git-объекты и возможность слияния.
Оба режима ничего не изменяют.

## Применение с явным разрешением

`--apply-safe` переносит только неконфликтующие изменения неконтрактных
Python-файлов. При неизвестной истории, удалении файлов или изменении
критичных контрактов операция отклоняется целиком.

`--apply-three-way` уже реализует **ограниченное** трёхстороннее Git-слияние
неконтрактных Python-файлов. Нужны чистая feature-ветка клиента,
неизменённые исходные модули и проверяемые SHA исходной истории.

```bash
git -C ../client-api switch -c chore/primarykit-upgrade
python scripts/module_upgrade.py --source . --project ../client-api --three-way-plan --json
python scripts/module_upgrade.py --source . --project ../client-api --apply-three-way --json
git -C ../client-api diff --check
git -C ../client-api diff
# Затем — ревью, PostgreSQL-тесты, коммит и PR в репозитории клиента.
```

Инструмент подготавливает файлы и обновлённые отпечатки для записи, а при
обычной ошибке записи пытается восстановить предыдущие версии. **При аварийном
завершении процесса полной транзакционности файловой системы нет.**
Инструмент не создаёт миграции, коммиты, PR, не обновляет зависимости и не
деплоит проект. Модели, контракты API, права, миграции и изменения схемы БД
всегда требуют отдельного ревью. Успешный текстовый merge не гарантирует
семантическую совместимость.

Манифест с более новым полем `Module` (например, `job_handlers`) требует той же
или более новой версии `apps/core`: со старым ядром `Module(...)` падает с
`TypeError` при запуске, а doctor сообщает `invalid_manifest`. Обновляйте
`apps/core` раньше или вместе с такими модулями.

Режимы применения сверяют байты исходных модулей с закоммиченными объектами
`HEAD`: файлы, игнорируемые Git, и файлы с изменёнными переводами строк
отклоняются.

## Принятие проверенных контрактных изменений

Без дополнительных флагов `--apply-three-way` по-прежнему отклоняет любое
изменение контрактного файла (модели, сервисы, права, manifest, views и т. п.)
и любой изменённый модуль, у которого в источнике есть миграции. Контрактные
файлы инструмент **никогда не записывает** — ни с флагами, ни без них. Флаги
ниже лишь фиксируют решение человека в `primarykit-origin.json`.

1. Получите read-only отчёт (`--json`, `--three-way-plan`).
2. В feature-ветке клиента человек читает каждый контрактный diff и размещает
   изменения вручную: изменённые только в источнике файлы копирует,
   изменённые с обеих сторон — сливает вручную; удалённые в источнике файлы
   удаляет. Результат коммитится.
3. Запустите применение, перечислив проверенные модули:

```bash
python scripts/module_upgrade.py --source . --project ../client-api \
  --apply-three-way --accept-reviewed tasks kanban \
  --merged-path kanban/services.py \
  --keep-client-migrations tasks --json
```

- `--accept-reviewed MODULE...` — модули, контрактные изменения которых уже
  проверены и размещены в клиенте.
- `--merged-path MODULE/PATH` (повторяемый) — каждый вручную слитый файл
  принятого модуля, который намеренно отличается от источника.
- `--keep-client-migrations MODULE...` — принятые модули, сохраняющие уже
  применённую клиентскую историю миграций (см.
  [контракт миграций](bundled-migration-contract.md)).

Обычные неконтрактные Python-файлы принятого модуля сливаются автоматически,
как и раньше. После успеха в `primarykit-origin.json` обновляются отпечатки,
SHA источника модуля, версия модуля (читается из `pyproject.toml` исходного
коммита, а не из рабочей копии) и `module_migration_policies`.

Операция отклоняется целиком, ничего не записывая, если:

- контрактное изменение источника не размещено в клиенте;
- файл изменён с обеих сторон, но не подтверждён через `--merged-path`;
- `--merged-path` не соответствует проверенному двустороннему изменению
  или указывает на непринятый модуль;
- история источника отсутствует, не является предком или не совпадает с
  записанными отпечатками; базовый снимок модуля неизвестен;
- удалённый в источнике файл всё ещё присутствует в клиенте;
- `primarykit-origin.json` — символическая ссылка; версия источника или
  клиентские `module_versions` не читаются;
- история миграций `bundled`-модуля отличается, а решение о ней не принято.

**Чего флаги не делают:** не проверяют качество ревью (инструмент верит
утверждению человека), не переносят `tests/` и не-Python файлы (они вне
отпечатков — переносите вручную, иначе устаревший тест проверяет старый
контракт), не создают и не применяют миграции. После принятия клиент сам
выполняет `makemigrations`, ревью и `migrate` на копии БД.

## Что проверено и что нет

`scripts/ci_release_upgrade.py --baseline ID` для каждого из трёх коммитов из
`scripts/release_baselines.json` генерирует клиента генератором **того**
коммита, создаёт клиентские миграции, заполняет PostgreSQL (задание Tasks,
Order, PaymentIntent), коммитит клиентские правки и обновляет проект до
текущего каталога описанным выше способом. Проверяется: клиентские правки
сохранены, непроверенных изменений источника не осталось, отпечатки
совпадают с байтами источника, ранее применённый реестр миграций не изменён,
строки данных целы, `makemigrations --check`, read-only
`migration_adoption --verify-postgres --strict`, doctor, Django check и pytest
клиента на PostgreSQL.

Ограничения этого свидетельства:

- «ревьюер» в сценарии — скрипт: он копирует контрактные файлы, изменённые
  только в источнике, сливает двусторонние через Git и переносит
  неизменённые тесты и файлы инструкций для агентов. Он заменяет человека
  только в CI;
- базовые точки — неизменяемые коммиты защищённого `main`, закреплённые по
  полному SHA. Git-тегов и GitHub-релизов пока нет, это **не** SemVer-релизы;
- покрыты только `tasks`, `kanban`, `deals`, `inventory` (standalone),
  `orders`, `payments`;
- в истории ещё нет обновления, меняющего схему, поэтому обновления с
  миграцией данных не доказаны; откат не проверяется;
- смена режима tenant/standalone не поддерживается.

[контракт миграций](bundled-migration-contract.md),
[issue #89](https://github.com/RoshihOPM/primarykit/issues/89) и
[#88](https://github.com/RoshihOPM/primarykit/issues/88) (оба открыты).
Совместимость между официально выпущенными версиями не доказана: таких
версий ещё нет, а обновления реальных клиентов человеком не проводились.

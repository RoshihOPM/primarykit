# Контракты совместимости скопированных модулей

PrimaryKit распространяет исходный код, а не устанавливаемую runtime-библиотеку. Любое изменение в клиентском backend требует отдельного PR и собственных миграций.

## Что считать контрактом

- `manifest.py`: стабильное имя модуля, обязательные зависимости, URL prefixes и режимы установки
- HTTP/OpenAPI: маршруты, методы, коды ошибок, сериализация, проверка прав, обратная совместимость
- Application layer: публичные команды, идемпотентность, транзакционные границы и события
- Data layer: имя таблицы, FK, ограничения, индексы, колонки, режим `standalone`/`tenant`
- Configuration: имена переменных, явные значения по умолчанию, конфигурация инфраструктуры
- Package lockfile: версии библиотек и требование воспроизводимой сборки

## Изменения и версии

Версия источника в `primarykit-origin.json` информационная; она не является runtime-проверкой и не означает, что клиентский код равен последней версии каталога. Источник и клиент могут расходиться после первого копирования.

**Patch:** исправление без изменения контрактов. **Minor:** необязательная возможность с совместимым поведением. **Major:** смена схемы/транспортного контракта/семантики или удаление API. Изменение зависимостей и pinned schema mode всегда требует явного review независимо от номера версии.

Автоматическое копирование обновлений через `pip install -U`, `git pull` чужого исходника или применение миграций при запуске запрещено.

## Процесс переноса исправления в клиентский проект

1. Сравнить исходные файлы из выбранного тега/коммита с клиентскими кастомизациями; описать затронутые контракты и security-impact.
2. Подготовить отдельный клиентский PR, без перезаписывания местной бизнес-логики и миграций.
3. При изменении моделей создать новые миграции, проверить SQL/план обновления, backup, возврат и совместимость со старым кодом.
4. Проверить `uv sync --locked --all-groups`, `python -m apps.core.doctor --strict`, Ruff, pytest и PostgreSQL concurrency/IDOR-интеграцию для затронутых модулей.
5. Провести rollback/release review и отдельно согласовать production migration/deploy.

Нельзя обещать upgrade-safe перенос между `standalone` и `tenant` режимами Catalog/Inventory без отдельного плана миграции данных. Нельзя распространять типовые Commerce-модели как обязательную предметную схему клиентских проектов.

## Проверка изменения OpenAPI

После создания двух версий schema.json используйте source-only
`python scripts/contract_check.py before.json after.json --fail-on-breaking`.
Скрипт выявляет удалённые endpoints, новые обязательные параметры и исчезнувшие успешные ответы; он **не заменяет** тесты object-level прав или ручное ревью схемы.

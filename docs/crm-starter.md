# CRM Starter — независимые модули

```bash
uv run python scripts/new_project.py ../my-crm --name my-crm --preset crm
cd ../my-crm
uv run python manage.py makemigrations users audit storage organizations tasks kanban leads contacts deals crm_pipeline
uv run python manage.py migrate
```

Шаблон собирает **четыре независимых модуля**: Kanban, Leads, Contacts,
Deals, а также явный интеграционный адаптер `crm_pipeline`. Между самими
базовыми модулями нет прямых зависимостей и связей моделей. Только адаптер
создаёт опциональную привязку Deal → Card. Каждый можно
установить отдельно через `--apps` вместе с обязательным базовым Users.

Все API требуют JWT и ограничивают данные владельцем. Organizations/RBAC не
включают командные права для этих модулей автоматически.

- `/api/v1/kanban/boards/`, `columns/`, `cards/` — доски, колонки, карточки
- `POST /api/v1/kanban/cards/{id}/move/` — `target_column_id`,
  `expected_version`, необязательный `position` (от нуля)
- `/api/v1/leads/` — лиды и `/{id}/transition/` для смены статуса
- `/api/v1/contacts/` — независимые контакты
- `/api/v1/deals/` — сделки и `/{id}/transition/` для смены стадии
- `/api/v1/crm/pipeline/links/` — привязка Deal к Card (`deal_id`, `card_id`)

У лида есть необязательное `assigned_to`. Без Organizations назначить можно
только себя; с Organizations — также активного участника общей активной
организации. **Назначение не выдаёт прав чтения или редактирования:**
владельцем данных остаётся создатель. При подключённом Audit изменения
лида записываются в журнал.

Для редактирования применяется `PATCH` с `expected_version`;
конфликт возвращает HTTP 409. У сделок суммы хранятся в целых минимальных
денежных единицах: это не платёжный процессинг.

Для проекции сделки создайте Kanban-доску с единственным столбцом для каждой
стадии `open`, `negotiation`, `won`, `lost` (без учёта регистра), а затем
привяжите сделку к карточке в столбце её текущей стадии. После привязки
смена стадии Deals атомарно двигает Card в той же транзакции PostgreSQL.
Если столбец отсутствует/неоднозначен, переход откатывается; перемещение
карточки вручную на другую стадию запрещено. После создания привязки
переименование колонок этой доски через Kanban API также запрещено: это
защищает соответствие стадий при параллельных операциях.
Адаптер можно исключить из
проекта, устанавливая независимые `deals` и `kanban` отдельно.

Это backend starter, а не законченный Bitrix24. Нет фронтенда,
совместных досок, автоматической связи сделок и лидов, командных прав,
удаления персональных данных, аналитики воронки и платёжных операций.
Такие правила и интеграции реализуются внутри сгенерированного проекта.
Миграции генерируются и коммитятся клиентом.

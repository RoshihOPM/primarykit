# Владение миграциями модулей

PrimaryKit — copy-based генератор. Данные и история миграций принадлежат клиенту.
Этот документ описывает **текущую** схему, а не готовую поставку миграций.

## Контракт manifest.py

- `migration_policy="none"` (по умолчанию) — модуль не имеет собственной схемы.
- `migration_policy="client"` — миграции создаёт и коммитит проект-клиент.

Генератор и CI проекта выводят список приложений из манифестов с помощью
`python -m apps.core.migration_plan`, а не из списка в генераторе.

## Ограничения и следующие шаги

Исходные миграции пока **не поставляются**. Миграции уже существующих проектов
нельзя перезаписывать или удалять. Catalog и Inventory имеют разные схемы в
standalone/tenant-режимах, выбираемых до первого запуска миграций.

Перед переходом к версионируемым историям нужно зафиксировать модель схем,
выполнить проверки внешних ключей и миграции на реальных данных в PostgreSQL,
добавить линтер опасных миграций и безопасный путь адаптации старых клиентов.
Изменения модели и схемы не должны накатываться автоматически без review.

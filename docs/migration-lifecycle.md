# Миграции и владение схемой модулей

PrimaryKit создаёт независимые Django-проекты. История применённых миграций
и данные принадлежат клиенту; обновление исходников не может автоматически
переписывать клиентские миграции или применять `--fake`.

## Политики manifest.py

- `migration_policy="none"` — модуль не имеет своей схемы БД.
- `migration_policy="client"` — клиент генерирует, ревьюит и коммитит миграции.
- `migration_policy="bundled"` — исходный модуль поставляет проверенную
  историю миграций **для новых клиентов**.

Сейчас `tasks` использует `bundled` с `0001_initial.py`. Это пилот, а не
гарантия безопасной замены истории Tasks в давно работающем клиентском проекте.

## Совместимость и проверки

Catalog и Inventory имеют отдельные семейства моделей `standalone` и
`tenant`. Профиль фиксируется при генерации. Менять его на работающей БД
без явной миграции данных нельзя.

PostgreSQL-матрица CI покрывает первоначальную генерацию схем, повторный
`migrate` и сохранность некоторых записей. Обновления между историческими
официальными релизами ещё не подтверждены.

```bash
python -m apps.core.migration_plan
python scripts/migration_adoption.py --source . --project ../client-api
# Проверка реестра применённых миграций в режиме только чтения:
DATABASE_URL=postgresql://... python scripts/migration_adoption.py \
  --source . --project ../client-api --verify-postgres --strict
```

Инвентаризация лишь сверяет файлы, закреплённый профиль и, по запросу,
`django_migrations`. Совпадение реестра не доказывает корректность физической
схемы и сохранность данных.

Для завершения [#88](https://github.com/RoshihOPM/primarykit/issues/88)
нужны проверенные истории версий и PostgreSQL-тесты обновления с данными,
ревью зависимостей и `makemigrations --check --dry-run`. Проверка SQL через
Squawk уже запускается в CI. Изменения DDL и возможные блокировки таблиц
требуют отдельной оценки.
